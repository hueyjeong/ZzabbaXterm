# A02 승인한 작업의 공용 실행 기반 만들기
선행: A01

A01에서 승인한 작업을 A03에서 지정한 중앙 세션으로 전달할 고정 실행기, 인증 제어 채널, 작업별 중지·종료 증거를 만든다. A02는 UI 없는 공용 기반이다. AI 전용 터미널, 오른쪽 아래 영역, 별도 실행 모드는 범위에서 제외한다.

**준비물:** A01의 실제 제안 경로, C02의 SSM 세션 생성·정리 코드, 별도 권한 승격 없이 `uptime`이 가능한 승인된 Linux 시험 노드 두 개, 네이티브 Windows 11 및 Ubuntu 24.04 GNOME Wayland. 아래 명령은 구현 후 `app/`에서 실행한다.

## 인수 조건

- **Given** 로컬 UI가 승인한 고정 조회와 인증된 제어 채널이 있다. **When** 같은 승인을 두 번 소비하거나 다른 세션에 제출한다. **Then** 유효한 요청 하나만 원래 세션으로 전달되고 다른 세션에는 전송이 없다.
- **Given** 작업 중 사용자가 중지를 요청했다. **When** 작업 자식을 회수한 증거가 도착하거나 확인 전에 채널이 끊긴다. **Then** 같은 작업 ID로 각각 `종료됨` 또는 `종료 확인 불가`를 돌려준다.

## 구현 순서

1. **Red.** `src-tauri/src/ai/`에 승인 중복 소비, A 승인으로 B 실행 요청, 만료, 정책 변경, 종료·재연결 뒤 재사용을 검사하는 시험을 둔다. 유효한 첫 요청만 지정 세션에 전달되고, 불명확한 전달 결과를 재전송하지 않아야 한다.
2. **Green — 대상과 권한.** A01의 원본 결정을 근거로 A03의 로컬 UI가 확인한 백엔드 세션 ID·세대와 실행 승인 ID를 받는다. Rust는 원본 결정, 실행 승인 ID, 만료, 대상·세대, 정책 버전, 작업과 인자를 잠금 안에서 대조하고 실행 승인을 한 번 소비한다. CLI와 모델은 A01 제안만 제출할 수 있다. 실행·일반 PTY 입력은 각각 인증 제어 채널·사람의 입력으로 분리하고, AWS 자격 증명·금고·권한 설정은 로컬 인증 경계에 둔다.
   - **시험 노드 최초 준비:** `src-tauri/resources/ai/ZxtAiControl.json`에 운영자가 배포할 SSM `Session` 문서(`Standard_Stream`)를 작성한다. 제한된 시험 사용자로 실행하고 Linux 시작 명령은 `exec /usr/local/libexec/zxt-ai-control` 하나로 고정한다. 사용자 입력 파라미터와 일반 셸 폴백을 두지 않는다. 관리자가 `src-tauri/src/bin/zxt-ai-control.rs`에서 빌드한 Linux 실행 파일을 관리자 소유·시험 사용자 쓰기 불가로 설치한다. 제어용 `StartSession`은 승인한 노드와 해당 문서에만, 종료 권한은 자기 세션에만 준다. 문서 편집·배포와 IAM 변경은 운영자가 관리한다.
   - **채널 연결:** 사용자에게 보이는 중앙 세션에 연동할 때만 Rust가 C02의 기존 프로필·리전·대상으로 공식 CLI `aws ssm start-session`을 호출하고 제어 채널에만 `--document-name ZxtAiControl`을 지정한다. 이 채널은 UI 없는 전송 경로이며 중앙 셸을 새로 열거나 CSS 영역을 만들지 않는다. 별도 포트·SSH·SFTP는 사용하지 않는다. `src-tauri/src/ai/control.rs`가 이 채널의 유일한 입출력 소유자다. 실행기는 터미널 에코를 끄고 준비 메시지를 보낸다. 앱은 버전과 새 난수를 교환하고 채널을 계정·리전·노드 및 선택한 중앙 세션 ID·세대에 묶는다. 플러그인 시작 안내는 준비 증거가 아니다. 설치 누락·권한 거부·에코 해제 실패·협상 실패 시 해당 채널을 정리하고 제안만 남긴다.
3. **실행 범위.** Rust가 지원하는 작업 표에서 실행할 프로그램과 인자를 결정한다. 예: 승인된 노드의 신뢰된 설치 경로에서 `uptime`을 인자 없이 실행한다. 셸의 별칭·함수·사용자 PATH에 기대지 말고 실제 전달할 절대 경로도 승인 카드에 표시한다. 모델·CLI·채팅의 셸 문자열, 임의 경로·옵션·환경 변수는 실행기에 전달하지 않는다. 고정 조회와 사용자가 요청하고 작업 표에 명시된 방어·운영 작업만 허용한다. 상태 변경은 매번 정확한 대상과 인자를 확인하고 금고·승격 요구는 별도 사용자 흐름에 남긴다. 미등록·복합 명령은 검토로 끝낸다.
4. **규칙.** 기본은 명시 차단 → 정확히 허용한 조회 → 나머지 확인 순서다. Auto의 System One이 별도로 승인된 경우 해석·권고만 붙인다. 미설정·오류 때도 같은 규칙을 적용한다. Bypass는 사용자가 연 같은 세션·같은 대상·같은 조회와 인자에 대한 기존 승인만 재사용한다. 반복 때도 카드를 먼저 표시하고 새 실행 ID를 한 번만 소비한다. 대상 변경·재연결·정책 변경·Bypass 해제 시 반복 허용을 폐기한다. 새 요청은 사용자가 시작한다.
5. **입출력·중지.** 준비 이후에는 개행으로 끝나는 길이 제한 JSON 프레임만 교환한다. `start → started → output(0회 이상) → exited` 순서이며 각 프레임에 채널 난수·작업 ID·방향별 순번을 넣는다. 실행기는 직접 시작한 고정 작업 자식의 stdout/stderr를 별도 파이프로 읽고 바이트를 Base64 `output`으로 전달한다. 자식이 출력한 JSON, 플러그인 안내, PTY 에코는 제어 프레임이 아니다. 채널·ID·순번·상태가 다르거나 프레임이 잘리면 처리를 중단한다. 중지는 해당 작업의 `stop`만 보내고 `중지 요청됨`을 반환한다. 실행기가 소유 자식을 중지·회수한 뒤 보낸 인증된 `exited`만 `종료됨`의 증거다. 확인 전 단절은 `종료 확인 불가`다. 채널 닫기 시 소유 자식과 해당 채널만 정리하고 반복 승인을 폐기한다. 중앙 셸과 다른 세션은 유지한다.

## 검증과 완료 증거

6. **자동:** 구현 후 `cargo test --manifest-path src-tauri/Cargo.toml`로 승인 소비·정책·프레임 검증을 확인한다. 잘못된 작업 ID 또는 자식 stdout으로 위조한 `exited`를 넣어 종료로 인정되지 않는지 검사한다. **실기기:** A03에서 두 OS의 승인된 노드 A·B로 최초 시작·중복 거부와 실제 자식 시작 건수를 확인한다. 허용된 고정 시험 대기 작업으로 중지 후 회수와 확인 전 채널 단절을 각각 재현한다. 작업 ID별 시작·회수 건수와 종료 증거를 기록하고, 종료 전후 A와 B의 중앙 세션이 유지되는지 확인한다. 인수는 [A03의 T7](03-shared.md#검증과-완료-증거)에 기록한다. 현재 제품 인수는 `미실행`이다.
