# A01 실제 채팅과 로컬 CLI에서 작업을 제안하고 대상 확인하기
선행: C02

사용자는 오른쪽 위에서 실제 모델과 대화하고, 채팅이나 로컬 CLI로 제안한 작업을 같은 화면에서 확인한다. 이 티켓의 끝은 승인 결정이다. 승인해도 원격 세션을 열거나 PTY에 쓰는 바이트는 0이다.

**준비물:** C02의 연결 목록·마법사와 승인된 비운영 관리 노드 두 개, Windows 11 및 Ubuntu 24.04 GNOME Wayland, 사용자가 설치한 로컬 Ollama와 로컬 모델 하나. 아래 명령과 경로는 구현 시점에 사용할 것이며 명령의 작업 디렉터리는 `app/`이다.

## 인수 조건

- **Given** 사용자가 일반 대화용 로컬 모델을 선택하고 전송을 승인했다. **When** 임의의 시험 단어를 알려 준 뒤 다시 묻는다. **Then** 오른쪽 위에 앞 대화를 반영한 실제 응답이 오고 아래에는 `대기`가 유지된다. 공급자가 꺼졌다면 연결 오류와 미전송/실패 상태를 표시하며 메인 셸은 계속 쓸 수 있다.
- **Given** 같은 대상에 같은 가동 시간 조회를 CLI와 채팅에서 각각 제안했다. **When** 두 카드를 연다. **Then** 두 카드 모두 같은 실제 노드·`uptime`·한국어 해석을 표시한다. 취소, 차단, 이중 승인, 승인 대기 중 대상 교체는 모두 원래 요청을 실행할 권한을 남기지 않는다.

## 구현 순서

1. **Red.** `src-tauri/src/ai/`에 두 출처의 동일 요청, 위조한 승인 필드, 존재하지 않는 대상, 중복 승인, 같은 표시명의 다른 노드로 교체하는 사례를 작성한다. `src/features/ai/`에는 대화와 제안 카드가 서로의 입력 또는 터미널 입력을 호출하면 실패하는 Vitest를 둔다.
2. **실제 CLI.** `zxt register`는 연결 설정 JSON을 표준 입력으로 받아 앱 창이나 접속 시험 없이 같은 앱 저장소에 새 대상을 추가한다. 응답은 대상 `id`와 문자열 `generation`이다. 기존 대상 ID로 등록하면 오류를 반환하고 저장본은 유지한다. `zxt list`는 앱이 실행 중일 때 로컬·SSM 연결의 `id`, `displayName`, `method`, `generation`을 반환한다. `zxt propose`에는 `{"targetId":"dev-a","generation":"1","operation":"uptime"}`처럼 목록에서 받은 ID와 개정 번호를 보낸다. 기본 창에서 같은 대상을 선택하고 **CLI 제안 열기**를 눌러 접수된 제안을 검토한다.
   입력 예: `{"version":1,"group":{"id":"dev","displayName":"개발"},"target":{"id":"dev-a","groupId":"dev","displayName":"개발 셸","defaultMethod":"ssm","ssm":{"profile":"dev","region":"ap-northeast-2","instanceId":"i-0123456789abcdef0"}}}`. 등록은 로컬·SSM·직접 SSH(수동 비밀번호 입력·키 파일·Agent)를 지원한다. SSH-over-SSM, 저장된 SSH 비밀번호 인증, Windows 로컬 시작 디렉터리의 UNC·확장·장치 경로는 각각 오류로 반환한다. 경로와 참조의 형식만 검사하며 파일 존재, 서버 도달 여부, 인증 성공, 호스트 키 등록 여부는 저장 조건이 아니다. 직접 SSH 설정의 기대 지문과 실제 호스트 키를 확인하는 절차는 [연결 등록](../02-connections/01-profiles.md#cli-연결-등록)을 따른다.
3. Rust 앱이 Windows에서는 현재 사용자 SID에만 허용하고 원격 클라이언트를 거부하는 명명된 파이프를, Ubuntu에서는 사용자 전용 런타임 디렉터리의 Unix 소켓(0600, 피어 UID 확인)을 연다. CLI도 서버의 소유자를 확인한다. 요청 하나당 길이 접두어·UTF-8 JSON 한 건으로 프레이밍하고 초과 길이·낯선 필드·기타 메서드를 거부한다. 같은 OS 사용자여도 승인자로 취급하지 않는다. 승인·저장·정책 변경 메서드는 소켓에 등록하지 않는다. 앱이 없을 때 `list`와 `propose`는 연결 오류로 종료한다.
4. **실제 대화.** 일반 채팅 설정에서 로컬 Ollama와 설치된 모델명을 사용자가 선택한 뒤 Rust가 [Ollama Chat API](https://docs.ollama.com/api/chat)에 따라 `POST http://127.0.0.1:11434/api/chat`으로 `model`, 현재 대화의 `messages`, `stream:false`만 보낸다. 프록시·리디렉션을 끄고 응답 크기·대기 시간을 제한한다. `message.content`는 React 텍스트로 렌더링한다. 터미널 기록·키 입력·연결 목록·인증 참조를 메시지에 합치지 않는다. 작업 제안 요청 때만 같은 API의 `format`에 작업 종류와 인자의 JSON Schema를 지정해 후보를 받는다. 대상은 모델이 아니라 사용자가 UI에서 선택한다. 파싱 실패는 제안 실패이고, 일반 답변에 섞인 JSON·명령은 텍스트다. 별도 선택 설정인 System One은 Auto의 해석·권고용이며 일반 채팅 설정만으로 활성화하지 않는다.
   Ollama에 `:local` 모델을 요청한다. 설치된 모델이 없어서 HTTP 404가 오면 `OllamaError::ModelNotInstalled`를 표시한다. 메시지 개수와 UTF-8 바이트는 직렬화 전에, JSON 본문은 전송 전에 제한한다. `OllamaError::RequestTooLarge`가 발생하면 기존 입력과 대화 이력을 유지한다.
5. **결정.** 두 출처를 Rust의 같은 판정 함수에 연결한다. 백엔드가 대상 ID를 프로필·리전·실제 관리 노드로 해석하고 제안 ID·연결 세대·작업 종류·검증된 인자·모드를 묶어 보관한다. 카드는 이 기록에서 만든 정확한 명령과 한국어 한 줄 해석(예: `uptime` → ‘선택한 노드의 가동 시간과 부하를 조회합니다’)을 표시한다. 제어문자는 이스케이프해 보인다. 명시 차단 우선, 정확히 등록된 조회, 나머지 사용자 확인 순이다. 미등록·복합·해석 불가 입력은 원문 검토만 가능하고 자유 문자열 실행 승인은 발급하지 않는다. 사용자가 요청한 지원 작업으로 다시 구성하면 별도 카드로 재확인한다. 기본 창에만 허용한 Tauri 명령에서 제안 ID로 원본을 다시 조회해 승인/거절을 한 번만 반영한다. 대상·세대·작업·정책 변경 시 이전 결정을 폐기한다. A01에는 승인 기록을 소비하는 실행기를 두지 않는다.
   개정 번호는 JavaScript에서도 손실 없이 비교하도록 문자열로 전달한다. 카드는 로컬 대상에 `내 PC`를, SSM 대상에 저장된 AWS 프로필 이름·리전·인스턴스 ID를 표시한다. 제안 전후와 결정 시점에 Rust가 기본 창의 문서 세대와 저장된 대상·개정 번호를 다시 확인한다. 모델 제안을 취소하면 같은 요청 ID의 HTTP 요청과 응답 읽기를 중단하고, 등록이 먼저 끝났으면 해당 카드만 제거한다. 키보드로 결정을 내리거나 요청을 취소하면 다음 상태 또는 제안 버튼에 포커스를 유지하며, 다른 입력으로 옮긴 포커스는 그대로 둔다. 모델 목록은 같은 루프백의 `GET /api/tags`에서 읽으며 사용할 수 있는 로컬 모델이 없으면 오류를 표시한다.

### 공통 로컬 리스너 계약

앱은 사용자 전용 `app` 서비스 하나에서 4바이트 빅엔디언 길이와 1–16384바이트 UTF-8 JSON으로 요청 한 건과 응답 한 건을 주고받는다. 연결 및 전송 기한은 각 3초다. 동시에 처리하는 연결은 최대 16개, 설정 파일을 읽는 작업은 최대 4개다. 직렬화된 요청이 한도를 넘으면 `invalidRequest`에 해당하는 종료 코드 2, 응답이 한도를 넘거나 설정 작업이 포화되면 `rejected`와 종료 코드 1을 반환한다.

현재 `method`는 `list`, `propose`만 허용한다. F02는 같은 서비스의 엄격한 `method` 분기에 접수만 추가하고 즉시 응답한다. 장기 편집과 완료 대기는 별도 앱 상태에서 진행한다. 등록·승인·자격·실행은 소켓 경계 밖이다.

CLI 제안 접수는 5분 후 만료된다. 유효한 같은 접수의 재전송은 ID와 만료 시각을 유지한다. 결정된 제안은 CLI에서 다시 접수하면 새 검토가 필요하다. 기본 창에서 조회 승인 정책을 바꾸면 이전 대기 카드를 폐기해 공용 32개 한도를 즉시 비운다. 카드 ID별 첫 승인·거절·취소는 대기 한도와 별개로 최근 32건까지 보관한다. 같은 결정 요청을 재전송하면 기존 검토 범위와 만료를 다시 확인한 뒤 기록된 결정을 반환한다. 응답이 유실되면 기본 창이 쓰기를 반복하지 않고 제안 ID의 결정을 다시 읽는다. 대상 또는 정책이 바뀐 뒤에도 최초 문서에서만 만료 전 결정 이력을 읽기 전용으로 표시한다.

## 검증과 완료 증거

6. **자동:** `cargo test --manifest-path src-tauri/Cargo.toml`과 `npx vitest run src/features/ai`로 판정표·IPC 거부·UI 상태를 확인한다. **실기기:** 별도 네이티브 터미널에서 빌드한 CLI로 앱이 닫힌 상태에서 연결을 등록한 뒤 `npm run tauri dev`로 앱을 열어 트리를 확인한다. 목록 → 제안 → 로컬 승인 순으로 진행하고, 같은 조회를 실제 채팅에서 요청한다. 일반 대화 두 턴, 공급자 중단, 승인 직전 노드 변경, 명시 차단도 촬영한다. OS·모델명·두 출처의 카드·결정·세션 수와 PTY 쓰기 건수 전후를 비밀 없이 남긴다. 실제 공급자 또는 장비가 없으면 해당 행은 `미실행(사유)`이다. macOS는 후속 실기기 검증이다.
