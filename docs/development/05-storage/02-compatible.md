# S02 S3 호환 HTTPS 서비스에 전용 키로 연결하기

선행: S01

사용자 결과: 사용자는 회사 AWS 프로필과 별도로 지정한 HTTPS 서비스에서 버킷·접두어를 열고 객체를 전송한다. 호환 서비스 인증이 거부돼도 회사 AWS 키나 다른 서비스 키가 전송되지 않는다.

준비물: Windows 11·Ubuntu 24.04 GNOME Wayland, 승인된 비운영 S3 호환 서비스와 시험 버킷, 서비스의 HTTPS 주소·서명 리전·지원 주소 방식·신뢰 CA, 해당 서비스 전용 시험 키와 거부용 시험 신원. 양쪽 주소 방식을 실제로 지원하는지 서비스 문서·DNS·인증서로 확인한다. S01 외 별도 SSH·금고 티켓은 필요 없다. 아래 명령은 구현 시점의 `app/` 기준이다.

## 연결

1. 오른쪽 **파일 → 파일 연결 → S3 호환 HTTPS**에서 서비스 ID·별칭·HTTPS 출처·서명 리전·주소 방식을 입력하거나 기존 설정을 불러온다.
2. 키가 없으면 **키 등록**을 선택해 네이티브 창에 액세스 키 ID와 비밀 키를 입력한다. 또는 같은 서비스와 출처에 미리 등록된 키링 항목 ID를 사용한다. 등록만으로 연결하거나 설정을 저장하는 동작은 없다. 등록 결과 확인 불가 시 OS 금고의 `ZzabbaXterm S3 · <항목 ID>`를 대조한다.
3. **전체 탐색**은 기본 출처의 버킷 목록을 한 번 요청한다. 전체 목록 권한이 없는 키는 **버킷 직접 열기**를 선택하고 버킷·접두어를 입력한다. 버킷 직접 열기는 그 버킷의 객체 목록을 한 번 요청하며, 성공한 첫 페이지를 그대로 표시한다. 이 연결은 같은 버킷의 접두어만 탐색한다. 새 설정과 변경 내용은 선택한 요청이 성공한 뒤 저장된다.

TLS는 SDK의 신뢰 체인과 실제 서버 이름을 검증한다. 프로세스 시작 환경에 `SSL_CERT_FILE` 또는 `SSL_CERT_DIR`이 있으면 SDK의 기본 인증서 로더가 그 설정을 사용할 수 있다. 키 저장이 잠겨 있으면 먼저 운영체제에서 잠금을 해제한다.

## 인수 조건

- Given 서비스 주소·리전·주소 방식과 이 대상에 묶인 키 참조 / When 시험 객체를 업로드하고 접두어 목록에서 다운로드 / Then 요청은 설정한 버킷 주소로만 가고 내려받은 바이트가 원본과 같다.
- Given HTTP 주소, 서버 이름과 불일치하는 인증서, 타 서비스 키 참조 또는 취소한 키 접근 / When 연결 테스트 / Then 승인되지 않은 호스트로 전송된 서명 요청은 0건이다. 실패 이유와 입력한 비밀 아닌 설정은 남는다.
- Given 전용 키에 대해 403이 반환됨 / When 오류를 표시 / Then 해당 엔드포인트·리전·키 참조 별칭과 실제 오류 코드가 보인다. 회사 SSO 로그인, 기본 키 탐색, 다른 호스트로 재서명은 일어나지 않는다.
- Given 기본 출처에서는 목록이 열리지만 가상 호스트의 버킷 인증서 이름이 다르다 / When 버킷 직접 열기 / Then 해당 버킷에 서명한 HTTP 요청을 보내기 전에 실패하고 설정과 탭을 게시하지 않는다.
- Given 지정한 버킷과 접두어에만 목록 권한이 있다 / When 버킷 직접 열기 / Then 서비스 전체 목록 요청 없이 승인한 버킷 첫 페이지가 열린다.

## 구현 순서

1. **Red.** `app/src-tauri/src/storage/compatible.rs`에서 `https://store.example.test`와 버킷 `sample`로 path-style의 `store.example.test/sample/...`과 virtual-hosted의 `sample.store.example.test/...`를 각각 검사한다. 격리된 전송 기록기와 가짜 표식 키를 사용해 잘못된 참조·다른 호스트 리디렉션·403 때 기본 AWS 공급자 호출과 외부 송신이 0인지 확인한다. `app/src/features/storage/`의 Vitest에서 AWS 유형에는 프로필만, 호환 유형에는 서비스 설정만 남는지 검사한다.
2. **Green — 설정.** S01의 객체 목록·전송 화면은 재사용하고 AWS 연결과 호환 연결을 별도 타입으로 둔다. Rust에서 HTTPS, 호스트·포트, 리전, 주소 방식, 키 참조의 소유 대상을 검증한다. URL 사용자 정보·쿼리·프래그먼트를 거부한다. 별칭과 다른 실제 주소를 확인받으며 엔드포인트 변경 시 이전 키 참조를 자동 이관하지 않는다.
3. **Green — 키 보관.** 이 티켓에서 Windows Credential Manager와 Linux Secret Service를 지원하는 Rust `keyring` 계열 백엔드를 OS별로 선택하고 해당 빌드 기능을 활성화한다. 서비스별 항목에 액세스 키 ID·비밀 키를 함께 보관하고 연결 파일에는 대상에 묶인 불투명 항목 ID만 쓴다. 네이티브 보안 입력 또는 사용자가 미리 등록한 해당 항목의 선택을 사용해 Rust에서만 값을 읽는다. 금고 잠김·항목 누락·사용 취소 시 멈춘다. OS 저장소가 없으면 파일·환경변수로 대신하지 않는다. 다른 티켓의 Bitwarden CLI나 SSH Agent를 호출할 필요가 없다.
4. **Green — SDK 경계.** AWS 프로필 설정을 복사하지 말고 [S3 클라이언트 설정](https://docs.rs/aws-sdk-s3/latest/aws_sdk_s3/config/struct.Builder.html)에 대상의 `endpoint_url`, `region`, `force_path_style`과 해당 항목만 읽은 명시적 `credentials_provider`를 지정한다. virtual-hosted는 버킷 접두사가 붙은 최종 DNS 이름·인증서까지 확인한다. 서명 전에 최종 스킴·호스트·포트가 선택 방식으로 계산한 값과 맞는지 검사한다. SDK가 호환되지 않는 버킷 이름을 path-style로 바꾸면 선택한 방식과의 불일치로 표시한다. 다른 출처 리디렉션·기본 AWS 엔드포인트 재시도는 차단한다. 신뢰 체인·서버 이름 검증은 유지하고 403·서명 리전 불일치·TLS 실패를 구분한다. UI에는 비밀·서명 헤더 대신 대상과 오류 코드만 반환한다.
5. **자동 검증.** `cargo test --manifest-path src-tauri/Cargo.toml storage`와 `npx vitest run src/features/storage`로 S01 키 보존·실패 처리와 S02 주소/인증 사례를 함께 확인한다. 민감 헤더를 저장하지 않는 기록기로 도착한 호스트/경로, 거부 전후 접근한 공급자 종류와 횟수만 비교한다.
6. **실기기 시연(T6 호환).** 두 OS에서 시험 서비스가 지원하는 주소 방식을 선택하고 새 접두어에 `한글.txt` 업로드→목록→다운로드를 수행한다. Windows `Get-FileHash -Algorithm SHA256`, Ubuntu `sha256sum`으로 원본과 수신본의 SHA-256을 비교한다. 거부용 시험 키로 반복해 같은 서비스의 거부 상태를 확인한다. OS·서비스/SDK 버전·익명화한 HTTPS 주소·리전·주소 방식·키 참조 별칭·두 해시·오류 코드를 기록한다. 시험 서비스가 제공하지 않는 주소 방식은 그 조합에 한해 `미실행(서버 구성)`으로 남긴다. AWS 성공이나 로컬 모의 서버 응답은 이 실서비스의 완료 증거가 아니다.
