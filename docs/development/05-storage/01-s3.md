# S01 회사 SSO 프로필로 AWS S3 객체 전송하기

선행: C02

사용자 결과: 사용자는 왼쪽 연결 트리에서 등록된 S3 대상을 열고 오른쪽 **파일** 탭에 고정된 S3에서 버킷과 접두어를 탐색한다. `한글.txt`를 올리고 내려받는 동안 중앙 터미널과 좌우 분할은 그대로 사용할 수 있다. SSH·SFTP·금고 기능은 선행 조건이 아니다.

준비물: 네이티브 Windows 11·Ubuntu 24.04 GNOME Wayland, C02에서 선택·재로그인할 수 있는 비운영 IAM Identity Center 프로필, 목록·쓰기·읽기가 승인된 시험 버킷과 비어 있는 접두어, 접근이 거부되는 별도 시험 대상, 원본 파일과 빈 다운로드 위치. 아래 명령은 구현 시점에 `app/`에서 사용한다.

## 인수 조건

- Given 선택한 프로필·리전과 시험 버킷 / When `한글.txt`를 업로드하고 목록에서 선택해 다운로드 / Then 전체 키가 일치하고 원본과 수신본의 바이트 수와 SHA-256이 같다.
- Given SSO 로그인은 유효하고 역할 자격 증명만 만료 / When 다음 목록을 요청 / Then 같은 프로필의 공급자가 임시 자격 증명을 다시 발급받는다. SSO 세션도 만료됐다면 재로그인을 요청한다. 유효한 신원에 대한 `AccessDenied`는 권한 거부다.
- Given 접근이 거부되거나 다운로드 도중 연결이 끊김 / When 서버 오류 또는 잘린 본문을 수신 / Then 해당 엔드포인트·프로필과 실패 단계가 보인다. 다른 자격 증명으로 보낸 요청은 0건이며 기존 로컬 파일은 그대로다.
- Given 중앙에 두 SSH 터미널이 있고 왼쪽 **SFTP 파일** 보기가 포커스된 SSH를 따라가는 중 / When 트리에서 등록된 S3를 열어 접두어로 이동하고 다른 SSH에 포커스를 준 뒤 같은 S3를 다시 연다 / Then S3는 중앙의 자기 탭에 열리고 SFTP 보기는 포커스된 SSH를 따른다. 같은 S3를 다시 열면 새 연결 없이 기존 탭으로 이동해 같은 세션·버킷·접두어가 보인다. 다른 탭과 탭 그룹 배치는 그대로다. 배치 실기기 기준은 [F02](../03-files/02-editor.md#파일-브라우저-배치와-세션-검증)에 기록한다.

## 구현 순서

1. **Red.** `app/src-tauri/src/storage/`에 선택한 프로필 공급자만 호출하는 검사와 `실험//한글.txt`, 공백·`+`·`%`가 든 키의 목록→선택→요청 보존 검사를 둔다. 연속 페이지의 `next_continuation_token`, 빈 목록과 403, 다운로드 도중 읽기 오류를 별도 사례로 만든다. `app/src/features/storage/`에 선택 탭이 바뀌어도 작업 대상이 바뀌지 않는 Vitest를 작성한다.
2. **Green — 인증 경계.** Rust는 C02가 검증한 계정·역할·SSO 리전만 사용한다. [STS `GetCallerIdentity`](https://docs.aws.amazon.com/STS/latest/APIReference/API_GetCallerIdentity.html)를 저장된 작업 리전에서 호출하고 승인 계정과 일치할 때만 세션을 발급한다. 이후 같은 공급자가 유효한 캐시 토큰으로 역할 자격 증명을 다시 발급받는다. 토큰이 만료되면 C02에서 같은 프로필로 다시 로그인한다.
3. **Green — 탐색.** Rust가 발급한 탭 세션 ID로 요청의 창과 대상을 확인한다. `list_buckets`와 `list_objects_v2`를 사용하고 `prefix`, `delimiter("/")`, 연속 토큰으로 다음 페이지를 요청한다. 버킷 전체 목록 권한과 지정 버킷의 목록 권한은 다르므로 지정 버킷은 직접 열 수 있게 한다. 접두어·객체 행을 구분하고 응답의 원본 키를 선택값으로 유지한다. SFTP처럼 `..`를 정리하거나 OS 경로 구분자를 넣지 않는다.
4. **Green — 전송.** Rust는 승인한 열린 파일 핸들을 `put_object`에 전달한다. `get_object`는 승인한 디렉터리에 임시 파일을 쓰고 길이·체크섬을 확인한다. 새 파일은 이름이 비어 있을 때만 게시한다. 승인된 교체는 앱 편집기와 같은 잠금을 사용하고, 게시 직전에 원본의 신원·내용·접근 권한과 부모 디렉터리를 다시 확인한다. 외부 변경을 감지하면 전송은 미완료이며, 원래 이름으로 복구를 확인할 수 없으면 UI의 **다운로드 파일 확정** 오류에 보존 파일의 로컬 경로를 표시한다. 실패·취소 시 쓰기 핸들을 회수하고 복구에 필요한 파일은 남긴다. UI에는 단계·바이트 수·서비스 오류 코드와 필요한 경우 로컬 복구 경로를 돌려주고, 키 자료·토큰·서명 헤더는 기록에서 제외한다. API 기준은 [AWS SDK for Rust S3](https://docs.rs/aws-sdk-s3/latest/aws_sdk_s3/).
5. **자동 검증.** `cargo test --manifest-path src-tauri/Cargo.toml --lib storage`로 저장된 프로필 검증, 격리된 SSO 캐시, SDK 응답 대역과 임시 파일을 확인한다. `npx vitest run src/features/storage src/features/workspace/Workspace.test.tsx`로 저장된 연결 선택, 탭 이동 중 전송 유지 및 결과 표시를 확인한다. 로컬 창은 `storage::ipc::local_pane::tests`와 `S3StorageLocal.test.tsx`가 맡는다.
6. **실기기 시연(T6 AWS).** 두 OS에서 새 시험 접두어에 `한글.txt`를 업로드→목록→다운로드한다. Windows는 `Get-FileHash -Algorithm SHA256`, Linux는 `sha256sum`으로 원본·다운로드본을 각각 읽는다. 거부 대상에서도 요청해 표시된 프로필·리전·엔드포인트·오류를 확인한다. OS·SDK 버전·가린 프로필·전체 시험 키·두 해시·실제 거부 결과를 남긴다. 역할 갱신과 SSO 재로그인은 각 조건에서 따로 기록한다. 환경 부재는 `미실행(사유)`이며 S3 호환 서비스 결과는 S02에 남긴다.

## 앱 통합

- 스토리지 개설은 저장된 연결 대상 ID와 개설 ID를 받는다. 닫기는 같은 ID의 개설 또는 세션을 취소한다. 개설과 AWS 응답에는 시간 제한을 둔다. Windows에서 `HOME`과 `USERPROFILE`이 다르면 C02와 스토리지 공급자 모두 `USERPROFILE`의 SSO 캐시를 사용한다.
- 스토리지 세션은 연결 시험에서 확인하고 저장한 계정 ID가 현재 SSO 설정과 STS 응답 양쪽에 일치할 때 열린다. S3 전용 등록은 프로필·리전·버킷·접두어만 사용해 시험하며 SSM 노드가 필요 없다. 계정 ID가 없는 대상은 오른쪽 **파일**의 **연결 재시험**으로 시험하고 다시 저장한다.
- SSO 만료 때만 **SSO 재로그인**을 표시한다. Rust가 같은 대상의 계정·프로필·역할·SSO 설정을 다시 확인한다. 열린 세션의 로그인에 성공하면 기존 편집 핸들과 경로를 유지하고 목록을 다시 읽는다. 최초 개설 단계에서 만료된 경우에는 로그인 뒤 사용자가 같은 연결을 다시 연다. 실패 후 같은 대상으로 재시도할 수 있고, 파일 전송은 사용자가 다시 시작한다.
- 버킷 목록의 리전을 표시한다. 직접 열 때 `HeadBucket`이 다른 리전을 반환하면 해당 리전을 선택하고 다시 열 수 있다. 같은 리전 헤더를 확인한 뒤에는 실제 접두어의 `ListObjectsV2` 응답으로 목록 권한을 판단한다. 버킷 확인, 객체 목록, 전송은 선택 리전과 같은 고정 SSO 공급자를 사용한다. 버킷·접두어·리전 입력을 바꾸면 목록 요청에 성공할 때까지 전송할 수 없다. 한 줄 업로드 키 입력은 CR·LF가 포함된 붙여넣기를 거부하고 기존 키를 유지한다.
- Windows와 Ubuntu에서는 작업 창에 연결된 네이티브 확인창에 리전·버킷·전체 키를 표시한 뒤 파일 열기 또는 저장 대화상자를 띄운다. 승인 ID는 문서·세션·리전·버킷·전체 키·전송 방향에 묶이며 한 번만 사용할 수 있다. 탭 전환은 세션을 유지한다. 업로드 응답 전에 세션을 닫거나 연결이 끊기면 다시 전송하기 전에 대상 키를 확인한다.
- S3 탭은 왼쪽 로컬 창과 오른쪽 S3 창의 2단 구성이며, 폭이 760px보다 좁으면 위아래로 쌓는다. 로컬 창 승인 모델은 다음과 같다.
  - 루트: **로컬 폴더 열기**가 네이티브 폴더 대화상자(Windows `SHBrowseForFolderW`, Ubuntu GTK `SelectFolder`, 기타 rfd `pick_folder`)를 띄운다. Rust는 정규화한 루트 경로와 디렉터리 핸들을 S3 탭 세션마다 하나만 보관하고 새 루트 ID를 발급한다. 새 루트를 고르면 이전 ID는 무효가 되고, 탭 닫기·문서 이동·종료 때 승인을 폐기한다. 대화상자가 열린 동안 탭이 닫히면 고른 폴더도 승인하지 않는다. 전송 승인 중에는 대화상자를 열지 않는다. 승인한 루트가 옮겨지거나 이름이 바뀌면 `rootChanged`를 돌려주고 승인을 폐기한다.
  - 루트 범위: 드라이브 루트(`/` 포함), 사용자 홈(`%USERPROFILE%`, `$HOME`) 자체와 그 상위, 보호 폴더와 그 상위·하위는 승인하지 않고 `restricted`를 돌려준다. 보호 폴더는 Windows `%APPDATA%`, `%LOCALAPPDATA%`, `%PROGRAMDATA%`, `%windir%`, `Program Files` 계열, Unix `/etc`, `/usr`, `/bin`, `/sbin`, `/lib`, `/boot`, `/dev`, `/proc`, `/sys`, 공통으로 홈의 `.ssh`, `.config`, `.local`, `.aws`, `.gnupg`, macOS `~/Library`다. 홈 바로 아래 숨김 폴더(`.`로 시작)와 그 하위도 승인하지 않는다. 홈의 다른 하위 폴더는 허용한다.
  - 경로: `storage_local_list {sessionId, rootId, path}`의 `path`는 루트 기준 `a/b` 형식이다. 빈 구간, `.`, `..`, `/`로 시작하는 절대 경로, 드라이브 문자와 `:`(대체 데이터 스트림), `\`·UNC, NUL, Windows에서 끝의 점·공백, 장치 이름(`CON`, `PRN`, `AUX`, `NUL`, `COM0`~`COM9`, `LPT0`~`LPT9`, 확장자 앞부분 기준, 대소문자 무시), `< > " | ? *`, 제어 문자를 거부한다(`invalidPath`). OneDrive Files On-Demand 같은 클라우드 자리 표시자(`IO_REPARSE_TAG_CLOUD*`)는 링크가 아닌 폴더·파일로 다룬다. 데이터 회수가 필요한(`RECALL_ON_DATA_ACCESS`/`RECALL_ON_OPEN`) 클라우드 전용 파일은 목록에 `offline: true`로 표시하고, 업로드·다운로드 교체 대상이면 `cloudOnly`로 거부한다. 경로 속성으로 먼저 거르고, 연 핸들의 속성으로 데이터를 읽기 전에 다시 확인한다(기존 대화상자 경로 포함). 회수를 일으키지 않도록 데이터가 로컬에 있는 자리 표시자만 연다. 모든 구간은 링크·재분석 지점이 아닌 실제 디렉터리여야 하고, 정규화 결과가 루트 아래의 같은 경로여야 한다(대소문자·짧은 이름 별칭 거부). 목록은 이름·종류(`folder`/`file`/`link`)·크기·수정 시각을 최대 5000개까지 돌려주고 넘으면 `truncated`를 표시한다. 링크는 항목으로만 보이며 들어가기·전송을 거부한다.
  - 전송: `storage_local_select {sessionId, bucket, region, key, rootId, path, direction}`가 기존 승인 슬롯에 열린 파일을 넣고 승인 ID를 돌려준다. 이후 기존 `storage_upload`·`storage_download`를 그대로 쓰므로 버킷 확인, 키 검증, 탭당 한 건의 승인, 탭 닫힘 취소가 같다. 업로드는 루트 안의 일반 파일을 링크를 따라가지 않고 열고, 전체 키는 현재 접두어와 파일 이름이다. 다운로드 대상은 루트 안의 현재 폴더와 키의 마지막 구간이며 기존 다운로드 게시 규칙을 쓴다. 같은 이름이 있으면 네이티브 교체 확인을 띄우고 승인할 때만 교체한다. 새 파일 이름이 실행 확장자(`.exe .com .cmd .bat .lnk .pif .scr .cpl .msc .msi .msp .msix .appx .ps1 .psm1 .psd1 .vbs .vbe .js .jse .wsf .wsh .hta .reg .url .scf .inf .jar .dll .sh .command .desktop .appimage` 등, 대소문자 무시)이면 네이티브 확인을 띄운다. 업로드는 `HeadObject`(호환 스토리지 포함)로 같은 키를 확인하고 조건부 PUT을 보낸다. 404면 `If-None-Match: *`, 객체가 있으면 네이티브 교체 확인을 승인할 때만 받은 ETag로 `If-Match`를 붙인다. AWS 탭에서 `HeadObject`가 403이면(업로드 전용 역할) **S3 객체 확인 불가** 확인을 띄우고, 승인하면 `If-None-Match: *`로 보낸다. 호환 스토리지 탭의 403은 조건 헤더를 무시하는 서비스가 있으므로 확인 없이 업로드하지 않고 **객체 확인** 오류로 끝낸다. `HeadObject` 200에 ETag가 없거나 약한 ETag(`W/`)면 `If-Match`에 쓸 수 없으므로 **잘못된 서비스 응답**으로 업로드하지 않는다. `If-None-Match: *` PUT의 412는 **같은 키의 객체 있음**, `If-Match` PUT의 412·404 `NoSuchKey`와 조건부 PUT의 409 `ConditionalRequestConflict`는 **다른 곳에서 객체가 바뀜**이며 둘 다 덮어쓰지 않는다. 다른 409 코드와 조건 없는 PUT의 412는 일반 서비스 오류다. 조건 헤더를 지원하지 않는 서비스의 501 등은 조건 없이 다시 보내지 않고 그대로 오류로 표시한다. 조건 헤더를 무시하는 호환 서비스는 서버 쪽에서 덮어쓸 수 있다. 그 밖의 존재 확인 실패는 업로드하지 않고 **객체 확인** 단계 오류를 표시한다. 기존 **업로드** 대화상자 경로는 조건 없이 보낸다. 로컬 경로 거부는 원인(`rejected`)과 함께 전송 행에 표시한다.
  - Mark of the Web: Windows에서 S3 다운로드(로컬 창과 기존 대화상자 경로)는 게시 직전 임시 파일 핸들 기준으로 `Zone.Identifier` 스트림(`[ZoneTransfer]`, `ZoneId=3`, `HostUrl=about:internet`)을 기록한다. 이름을 바꿔 게시해도 스트림이 함께 간다. 스트림을 기록한 뒤 디스크에 반영한다. 기록 실패는 다운로드 실패로 만들지 않고 로그만 남기지만, 교체할 원본에 `Zone.Identifier`가 있었거나 확인할 수 없으면 표시 없는 파일로 바꾸지 않고 다운로드를 실패로 끝낸다. 다운로드 교체는 원본의 `Zone.Identifier` 스트림만 버릴 수 있고, 다른 대체 스트림·확장 특성이 있으면 교체하지 않는다. 편집기 저장은 새 표시를 만들지 않고 원본의 `Zone.Identifier` 내용을 그대로 옮긴다(F02).
  - 끌어 놓기는 전용 형식(`application/x-zzabba-local-file`, `application/x-zzabba-s3-object`)만 받는다. 탭 끌기와 OS 파일 놓기와 겹치지 않는다. 기존 **업로드**·**다운로드**의 파일 대화상자 경로는 그대로다.
- 파일 컨텍스트 메뉴의 **편집**은 보존 조건을 확인한 1 MiB 이하의 UTF-8 평문 객체만 연다. 저장은 열 때 받은 ETag에 `If-Match`를 붙인 PUT 한 번이다. 충돌 또는 결과 미확인 시 편집본을 유지한다. S3가 저장과 함께 비교하는 값은 현재 ETag이며, 버전과 객체 속성은 저장 직전에 별도로 확인한다.
- 객체 편집에는 다음 IAM 액션이 필요하다. 버전 관리가 켜져 있어야 하고 소유권은 `BucketOwnerEnforced`, 객체 잠금은 없어야 한다. 하나라도 없으면 편집이 거부된다.
  - 버킷: `s3:GetBucketVersioning`, `s3:GetBucketOwnershipControls`, `s3:GetBucketObjectLockConfiguration`
  - 객체(버전 지정 포함): `s3:GetObject`, `s3:GetObjectVersion`, `s3:GetObjectTagging`, `s3:GetObjectVersionTagging`, `s3:ListObjectAnnotations`, `s3:ListObjectVersionAnnotations`, `s3:PutObject`
  - 목록·탐색은 별도로 `s3:ListAllMyBuckets`, `s3:ListBucket`, `s3:ListBucketVersions`를 쓴다.
  - `s3:ListObjectVersionAnnotations`가 없으면 SDK가 이를 `GetObject` 단계의 403으로 보고하므로, 화면의 오류만으로는 부족한 권한을 구분할 수 없다. 편집이 403으로 실패하면 위 목록을 먼저 확인한다.
